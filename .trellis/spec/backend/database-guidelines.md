# Database Guidelines

> Supabase (managed Postgres). Client: `@supabase/ssr` for server-side, `@supabase/supabase-js` for types.

---

## What is and isn't relational

The game **save** is a single JSON document (game-design/data-model.md: `GameState` = character + world + dynasty + npcs + current_event + turn + rng_seed). **Do not normalize it into tables** — store the whole validated blob in one JSONB column. Only genuinely cross-row, queried data (the leaderboard) gets real columns.

## Schema (Supabase migrations)

```sql
-- supabase/migrations/0001_init.sql

create table saves (
  id uuid primary key default gen_random_uuid(),
  slot text not null,
  state jsonb not null,
  turn_number integer not null,
  updated_at timestamptz not null default now()
);

create index saves_slot_idx on saves(slot);

create table leaderboard (
  id uuid primary key default gen_random_uuid(),
  family_name text not null,
  tier text not null,              -- S | A | B | C | D | F (core-loop.md Victory Tiers)
  score integer not null,
  generations integer not null,
  achieved_at timestamptz not null default now()
);

create index leaderboard_score_idx on leaderboard(score desc);

-- RLS: anonymous access (hackathon demo — no auth required)
alter table saves enable row level security;
create policy "anon_saves" on saves for all using (true) with check (true);

alter table leaderboard enable row level security;
create policy "anon_leaderboard_read" on leaderboard for select using (true);
create policy "anon_leaderboard_insert" on leaderboard for insert with check (true);
```

## Reading/writing saves — always validate at the boundary

The DB stores JSONB; the app trusts only Zod-parsed objects.

```ts
import { GameState } from "@/lib/game/schema";
import { createClient } from "@/lib/db/client";

export async function loadSave(id: string): Promise<GameState | null> {
  const supabase = await createClient();
  const { data, error } = await supabase
    .from("saves")
    .select("state")
    .eq("id", id)
    .single();
  if (error || !data) return null;
  return GameState.parse(data.state);
}

export async function upsertSave(id: string, slot: string, state: GameState) {
  const validated = GameState.parse(state);
  const supabase = await createClient();
  await supabase.from("saves").upsert({
    id,
    slot,
    state: validated,
    turn_number: validated.turn_number,
    updated_at: new Date().toISOString(),
  });
}
```

## Migrations

- SQL migrations live in `supabase/migrations/`. Run `supabase db push` or `supabase migration up`.
- A new field **inside** `GameState` needs **no migration** (it rides in the JSONB blob) — only update `lib/game/schema.ts`. `GameState` carries a `version` (data-model.md); when the blob shape changes incompatibly, migrate old blobs inside `loadSave`.
- A new **leaderboard column** → real SQL migration.

## Session & Save Reconnection

The game uses anonymous sessions — no login, no auth. Players reconnect to their save via a locally-stored ID.

### Flow

1. **First visit**: Server Action `newGame()` creates a save row, returns the `id`. Client stores `id` in `localStorage` under key `epochal-laurel-save-id`.
2. **Return visit**: Client reads `localStorage["epochal-laurel-save-id"]`, passes it to Server Actions to load/update the save.
3. **URL override**: `?save=<id>` query param overrides localStorage — used for sharing or QR-code demo links. If present, also update localStorage to this ID.
4. **Missing save**: If localStorage has an ID but the DB row is gone (e.g., expired/deleted), treat as first visit — create a new save.

### Implementation Notes

- The save ID is a UUID (generated by Postgres `gen_random_uuid()`).
- No server-side session, no cookies, no Supabase auth tokens.
- `slot` column in the `saves` table is reserved for future multi-slot support; for v1, always use `"default"`.
- The client is responsible for storing the ID; the server never sets cookies or headers for session tracking.

### Security Considerations

- Save IDs are UUIDs — unguessable, so knowing an ID = owning the save. This is acceptable for a hackathon demo.
- No rate limiting on save creation for v1 (acceptable for demo scale).

## Conventions

- Tables/columns: `snake_case`.
- All queries are async (Supabase client is HTTP-based).
- Keep all query functions in `lib/db/queries.ts`, never inline in actions.
- Use Supabase's `.rpc()` for multi-step operations that need atomicity.

## Common mistakes

- ❌ Spreading game state across many tables — it's a document; you'll fight the engine's single-object model.
- ❌ Persisting an unvalidated object — a malformed save corrupts every future load. Always `GameState.parse` in and out.
- ❌ Storing API keys or LLM transcripts in the DB.
- ❌ Using Supabase auth for this project — it's anonymous hackathon demo play via QR code.
